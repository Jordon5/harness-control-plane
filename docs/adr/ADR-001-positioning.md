# ADR-001: 定位为调度中台而非模型网关

- 状态：Accepted
- 日期：2026-09-14

## 背景

AI 编程工具的实际效果 = 模型能力 + 原生 harness（系统提示、工具实现、上下文策略、权限模型、任务循环）。

把不同厂商的模型统一接入一个通用 harness，会损失各家的原生优势。用户需要同时使用多个 harness，但缺少跨 harness 的任务编排、隔离、状态与合并能力。

存在两种可能路线：

1. **统一模型网关**：自建一个通用 agent loop，接入各家模型 API
2. **统一调度协议**：保留各家原生 harness，只统一编排层

## 决策

采用路线 2。本项目是**多 Agent Harness 中枢控制器**：

```text
核心控制器负责：调度什么、何时调度、在哪里执行、结果如何合并
Adapter 负责：某个具体 harness 如何工作
```

明确非目标：

- 不做统一模型网关
- 不实现自己的 agent loop 或工具集
- 不替代任一现有 harness

## 理由

- 保留每个 harness 的原生能力，避免"模型对了、工具链错了"的次优结果
- 各厂商 harness 迭代快，复用比追赶更现实
- 与用户已有的多工具、多线路现状（pi + 中转 + 多种模型）自然契合

## 后果

- 必须维护多个 adapter，且要应对各家 CLI 接口变化
- 无法统一中间过程格式，只能统一事件与结果协议
- 价值集中在编排、隔离、合并策略，而非模型调用本身

## 替代方案

- **统一模型网关**：实现简单、可控，但丧失原生 harness 优势，弃用
- **只用单一 harness**：无法满足多工具协同需求，弃用
