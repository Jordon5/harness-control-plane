# ADR-005: 首期 SQLite + Store 接口抽象

- 状态：Accepted
- 日期：2026-09-14

## 背景

系统需要持久化任务、执行节点、运行、事件、产物与审批记录，并要求进程崩溃后可查、可恢复。

首期是单机 CLI 工具，但后续可能扩展到多进程、多机器或 Web 服务。

## 决策

- 存储层通过 `Store` 接口抽象，核心逻辑只依赖接口
- 首期实现为 **SQLite**（单一本地文件 `.hcp/hcp.db`）
- 同时提供**内存实现**，供单元测试使用

首期表结构：

```text
tasks / stages / runs / events / artifacts / approvals
```

事件表按 `(run_id, id)` 建索引以支持日志跟随。

## 理由

- SQLite 零运维、单文件、事务完整，适合单机 CLI
- 接口抽象把"换存储"的成本控制在一个实现内
- 内存实现让单测无需磁盘与清理逻辑

## 后果

- 需自行管理 schema 迁移（首期可用版本号 + 顺序脚本）
- SQLite 并发写入受限，多进程场景需 WAL 模式或加锁
- 若未来上多机，需实现新 Store（如 Postgres），但调用方不变

## 替代方案

- **JSON/YAML 文件**：最简单，但无事务、查询弱、崩溃易损坏，弃用
- **Postgres**：能力过剩、部署成本高，弃用
- **直接上工作流引擎（Temporal）**：解决编排与持久化，但引入重依赖且不处理 harness 适配，后置
