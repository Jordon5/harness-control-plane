# ADR-006: 核心实现语言

- 状态：Accepted
- 日期：2026-09-14
- 更新：2026-09-15 决策为 TypeScript

## 背景

项目要管理跨平台子进程、解析多种输出流、通过 HTTP/SSE 对接本地服务、并以插件形式加载适配器。

核心语言一旦确定，M1 起所有代码都受其约束，因此需要在动手前定下。

## 候选方案

### TypeScript / Node.js（选定）

优点：

- 子进程管理、流式 I/O、SSE/HTTP 都是原生强项
- 与 pi、多数 CLI 工具链（Node 生态）同构，接入摩擦小
- npm workspaces 天然支持 adapter 包化与后续插件分发
- 类型系统可表达 interface/manifest 等契约

缺点：

- 需要 Node 运行时；单文件分发需额外打包
- `better-sqlite3` 为原生模块，跨平台需编译

### Python

优点：团队可能更熟悉；生态成熟；脚本化与快速原型方便

缺点：跨平台子进程与流解析需更多样板；分发与插件发现不如 npm workspaces 直接

### Rust

优点：单二进制分发、性能与可靠性最佳

缺点：开发速度慢、早期迭代成本高、生态对接各家 CLI 需更多手写

## 决策

采用 **TypeScript / Node.js** 作为核心实现语言。

## 决策依据

- 核心职责是"管子进程 + 解析输出流 + 插件加载 + 暴露 HTTP"，均为 Node 原生强项
- pi 等目标 harness 位于 Node 生态，接入摩擦最小
- npm workspaces 天然支持 adapter 包化与插件分发
- 单文件分发非首期需求，Rust 的权重不构成理由

## 后果

- 冻结 M1 代码形态为 TS
- `better-sqlite3` 为原生模块，跨平台需编译（见架构 §12 已知约束）
- 控制面（调度 / 状态 / 事件）不受语言制约：若将来数据面或分析层（用量、bad token）需要，可**独立选型**，通过 `Store` / HTTP 接口对接，而非重写核心

## 替代方案

- **Python**：优势在数据 / ML 生态，不在首期范围；子进程与插件机制摩擦更大，弃用
- **Rust**：性能与分发最佳，但迭代成本高、首期无单文件分发硬需求，弃用
