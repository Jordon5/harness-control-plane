# ADR-007: 首期是否暴露本地 HTTP API

- 状态：Accepted
- 日期：2026-09-14
- 更新：2026-09-15 决策为首期即暴露

## 背景

控制中台未来需要长时间跟随运行状态、支持 Web UI、远程调用或 CI 集成，这些通常需要一个本地 HTTP API。

首期目标是"用一个 YAML 跑通 DAG"，是否需要同时引入服务层，是范围问题。

## 候选方案

### A. 首期不做 HTTP API

- 只有 CLI，核心逻辑直接调用
- 未来需要时，在 core 之上加一层薄 HTTP 适配

优点：范围最小、无端口/鉴权/生命周期管理
缺点：若中途确定需要，需要重构入口

### B. 首期同时提供本地 HTTP API（选定）

- CLI 与 HTTP 共享同一 core
- 端点覆盖 run / status / logs / diff / merge

优点：为 UI 与远程调用铺路；支持"浏览器跟随进度"；是控制面与外部集成的稳定边界
缺点：需要处理鉴权、并发、服务生命周期；推迟 MVP

## 决策

采用**方案 B：首期即暴露本地 HTTP API**。

- CLI 与 HTTP 共享同一 core，端点覆盖 run / status / logs / diff / merge
- core 不依赖 CLI 上下文（不直接 print、不直接读 argv）
- 鉴权首期从简（本地回环 + token），服务生命周期由 `hcp serve` 管理

## 决策依据

- 有明确的近期需求：长时间跟随运行状态、为后续 UI 与 CI 铺路
- core 本就是纯逻辑 + Store，加薄 HTTP 层成本低
- HTTP 是控制面与外部世界（网关打标、外部分析服务、CI）**唯一稳定的集成边界**，提前确立可避免将来重构入口

## 后果

- 需处理端口 / 鉴权 / 服务生命周期，MVP 完成时间略后移
- `hcp` 从"一次性命令"演进为"可常驻服务"，需考虑并发任务与会话
- 架构文档需补充服务层描述（待补）

## 替代方案

- **方案 A（首期不做）**：重构风险虽低，但放弃了长期跟随状态等即时价值，且外部集成边界被迫后置，弃用
