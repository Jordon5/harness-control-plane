# ADR-012: 定位演进为平台工程

- 状态：Accepted
- 日期：2026-09-16

## 背景

原始定位（ADR-001）是"**薄控制器**"：只统一调度协议，不统一模型 API、不替代任何 harness。彼时的范围仅 D1–D5（编排、隔离、路由、审批、观测）。

随着需求演进，规划中陆续纳入了超出"薄控制器"范畴的能力：

| 新增能力 | 为什么不再是"薄" |
|---|---|
| D6 用量/成本、D7 质量归因 | 观测与分析层，非执行编排 |
| D8 意图 → DAG 生成 | AI 生成编排，非执行编排 |
| D9 上下文工程（项目级知识） | 记忆层，控制器不管理知识 |
| HTTP API + `serve` 常驻（ADR-007） | 从一次性命令变为服务 |
| TUI / WebUI 多前端 | 平台化信号 |
| 多 Project 预留（ADR-010） | 跨仓库平台形态 |

结论：规划早已越过"薄控制器"，实为平台；但实现仅落地约 1.5 个能力域。**规划与实现不对称**——规划领先，实现滞后。

## 决策

明确将本项目按 **平台工程** 开发与打磨（而非"薄控制器"）。

- 定位表述：**可扩展的多 Agent Harness 调度平台**
- ADR-001 的**内核约束不变**（不统一模型 API、不替代 harness、只统一调度协议）；改变的是**范围认知**与**工程标准**

## 平台工程的首要维度（作为后续设计标准）

1. **抽象边界**：供给方（adapter / RouteStrategy / Store，复数可插拔）与消费方（CLI / HTTP / TUI / WebUI / CI，多前端）分列两侧；平台本体只做调和，**不依赖任一具体 provider 或 consumer**。
2. **契约与版本**：平台价值 = 契约稳定性。`@hcp/contracts`、事件协议、YAML schema、HTTP API 均需版本演进策略（**当前最大空缺**）。
3. **扩展点与治理**：扩展点（adapter / 策略 / Gate / Store）需配套发现（registry）、能力声明（manifest）、隔离、可观测。

## 后果

- **审查标准提高**：接口冻结更谨慎（契约被多包依赖，改动成本 = N 倍）
- **节奏不变**：现有 R1（阶段留案）/ R2（影响图 + 增量测试）本就是平台工程做法，无需返工
- **风险提示**：规划已领先实现较多，**后续应少扩规划、多兑现实现**（M3–M6），把规划逐个落地为可运行能力
- M3 被赋予新含义：**平台的第一个内核**，调度器按"将来可被替换/扩展"的标准设计（`Scheduler` 接口，对齐 D1）

## 替代方案

- **维持"薄控制器"定位**：与已规划能力不符，且无法承载 D6–D9，弃用
- **重新收窄范围以回到"薄"**：放弃已确认的需求（用量、归因、上下文工程），与用户意图相悖，弃用
