## 1. 愿景

### 1.1 一句话

**让一个人能像指挥一支团队那样，调度多个原生 coding harness 协作完成一件编程任务。**

### 1.2 定位

**可扩展的多 Agent Harness 调度平台。** 不统一模型 API、不替代任何 harness，只统一**调度协议**：由平台决定"调度什么、何时调度、在哪里执行、结果如何合并"，具体 harness 保留其原生形态（见 ADR-001）。

> **从"薄控制器"到"平台"**（2026-09-16 定位演进，见 ADR-012）。
> 原始设想是"只统一调度协议"的薄控制器；随着 D6（用量成本）、D7（质量归因）、D8（意图生成）、D9（上下文工程）与 HTTP 服务、多前端（TUI/WebUI）进入视野，本项目已明确按**平台工程**开发与打磨。平台的三个首要维度：
>
> 1. **抽象边界**——供给方（adapter / 策略 / 存储，复数可插拔）与消费方（CLI / HTTP / TUI / WebUI / CI，多前端）分列两侧，平台本体**只做调和**，不依赖任何具体 provider 或 consumer（守 ADR-002 / 007 / 011）。
> 2. **契约与版本**——平台的价值 = 契约的稳定性；`@hcp/contracts`、事件协议、YAML schema、HTTP API 均需**版本演进策略**（当前最大空缺）。
> 3. **扩展点与治理**——adapter / RouteStrategy / Gate / Store 为扩展点，配套发现（registry）、能力声明（manifest）、隔离、可观测。

### 1.3 非目标

- ❌ 不做统一模型网关 / 通用 agent loop
- ❌ 不追求替代任一 harness
- ❌ 不服务团队 / 多租户（个人工具；团队形态见附录 A）

### 1.4 设计原则

> **MVP 是愿景的子集，不是权宜之计。**

每一条 MVP 决策都必须是完整愿景在该阶段的一个**切片**，而非将来要推翻重写的临时件。判断标准：今天省掉的能力，明天可以**增量补上**，而不是**推倒重来**。凡有"现在不做、将来补不回"的信息（如运行时的用量、prompt 版本、项目级上下文），必须在数据产生时就记录。

## 2. 用户与场景

### 2.1 主用户

**个人开发者**（单机、无团队）。具体处境：

- 手头同时使用 **pi / claude-code / codex**，计划扩展 kimi / dsh
- **Windows** 本地环境，模型流量走 `api.iottepa.cn` 中转
- 能且愿意手写 YAML（但不想长期手写——见 D8）
- **对成本敏感**（故"省钱"排第二）
- 目标：一个人像指挥一支团队那样调度多个 harness

**期望终局**：编排创作成本趋近于零——自然语言表达意图 → 轻量 AI 生成任务 YAML → 中台调度、注入任务态 → agent 完成当前节点（见 D8）。

### 2.2 Jobs-to-be-done

| 我想…… | 因为…… |
|---|---|
| 用一个定义让多个 harness 分工做一件事 | 单个 harness 不是每件事都最优 |
| 让它们并行干活、互不打架 | 手动开多个 worktree 太累且易冲突 |
| 一眼看到谁在做什么、花了多少 | 黑盒运行无法判断值不值 |
| 在合并前把关 | 不想让半成品污染主分支 |
| 知道哪个 harness / prompt 更划算 | 想持续调整策略而非凭感觉 |

### 2.3 关键场景

1. **分析→实现→审查**：pi 快速扫描、codex 实现、claude-code 审查，一条 DAG 跑完。
2. **并行实现**：两条互不重叠的写入任务同时跑，各自 worktree，最后分别合并。
3. **降级容错**：首选 harness 不可用/失败，自动落到次选，任务不中断。
4. **成本/质量回看**：跑完看这次花了多少、有多少是浪费，据此调整某 harness 的用法。

## 3. 成功标准

按优先级（决定默认路由目标函数与排序）：

| # | 标准 | 含义 | 度量 |
|---|---|---|---|
| **1** | **多 harness 协作效果好** | 编排产出的结果优于任一单 harness 单打 | 任务成功率 / 质量评分 vs 单 harness 基线 |
| **2** | **省钱** | 单位成功任务的成本下降 | 每成功任务的 token 成本 |
| **3** | **省时间** | 单位任务的墙钟时间下降 | 每任务 P50 墙钟，含并行度 |

> **直接后果**：默认路由策略的目标是 **效果优先，其次成本，再次速度**。这决定 `RouteStrategy` 的默认权重，也决定"省钱"虽排第二，但其**数据基础（用量采集）必须进 MVP**。

## 4. 能力域

每个能力域标注：完整愿景 → MVP 切片 → 是否产生债。

### D1 编排与调度

- **愿景**：YAML 定义 DAG；并行、依赖、超时、重试、条件分支、子任务；崩溃可恢复。
- **MVP 切片**：YAML → 拓扑排序 → 依赖就绪队列 → 并发上限执行；失败传播、超时、基础重试；**任务态注入**——每个 Stage 执行时组装上下文（goal、上游产物、owned_paths、完成判据）交由 agent，注入方式由 adapter 在 manifest 声明。
- **债？** 无。调度器藏在 `Scheduler` 接口后，将来可替换引擎（Temporal 等）。

### D2 隔离与工作区

- **愿景**：只读共享、写入 worktree、审查快照；`owned_paths` 所有权；重叠检测（串行或审批）。
- **MVP 切片**：只读主工作区 + 写入独立 worktree + `owned_paths` 重叠检测。
- **债？** 无。隔离级别是枚举，可扩展。

### D3 能力路由与降级

- **愿景**：按 manifest 能力匹配 + 可插拔策略（preferred / cheapest / fastest / round-robin）+ 健康度 + 降级。
- **MVP 切片**：能力匹配 + `preferred-first` + 首选失败自动降级。**默认目标函数 = 效果 > 成本 > 速度（见 §3）**。
- **债？** 无。策略是 `RouteStrategy` 实现，可增。

### D4 审批与安全边界

- **愿景**：Gate 体系（first-write / merge / push / destructive / path-conflict）+ 可配置策略。
- **MVP 切片**：`first-write` + `merge` 两个 Gate 的人工确认。
- **债？** 无。Gate 为注册式处理器。

### D5 可观测性

- **愿景**：事件流、实时跟随、过滤、回放、指标、追踪。
- **MVP 切片**：事件落库 + `hcp status/logs/diff` + **本地 HTTP API**（ADR-007，为跟随/UI/CI 铺路）。
- **债？** 无。事件模型（ADR-003）与 HTTP 边界是长期稳定的。

### D6 用量与成本

- **愿景**：按 run/stage/harness/model 统计用量与成本；对接外部网关（new-api）白拿成本；预算与对账（详见 development-plan §11 F1）。
- **MVP 切片（Must）**：**采集**——adapter 解析 harness 上报的 usage，落 `usage` 表；`UsageProvider` 接口（事件流 / 网关两实现位）。
- **后续（Should）**：**展示与估算**——`status`/API 读 `usage` 表并估算成本。
  - **采集与展示解耦**：展示只依赖 `Store`，不耦合任何具体功能。故为纯增量，晚加不还债。
- **债？** ⚠️ **若 MVP 不采集量，将来补不回**——故**采集进 MVP**。分析/网关/预算可后置。
- **控制面 ↔ 网关唯一接口点**：给流量打标（每 run 独立 key / 模型别名 / 网关记录的 header），否则网关按 key/model 聚合、对不上 runId。

### D7 质量归因与 Prompt 调优闭环

- **愿景**：四类浪费识别（重试 / 死循环 / 失败工具调用 / 空转探索）→ 定位 prompt 问题 → 调整某 harness 系统提示词 → 重跑看 delta（详见 development-plan §11 F2–F3）。
- **MVP 切片**：**不做分析**。仅**记录每次 run 的 config / prompt 版本**（`run.config_ref`）。
- **债？** ⚠️ **若 MVP 不记录 prompt/config 版本，将来无法回溯 delta 归因**——故**版本记录进 MVP**。分析层硬依赖事件流（网关做不到，见 development-plan §11 F2），可后置。
- **定位**：编排为主线，本域**不是独立子系统**——复用已有 Run / 事件 / usage / `config_ref` 机制串联而成（跑 → 改提示词 → 再跑 → 比对），属**用法**而非新功能。

### D8 编排生成（Intent → DAG）

- **愿景**：用户用自然语言表达意图 → 轻量 AI（如 pi）生成**规范的任务 YAML** → 中台校验、调度、注入任务态 → agent 完成当前节点。编排创作成本趋近于零。
- **MVP 切片**：**不做 AI 生成**，但把 YAML schema 设计到"AI 一次即可写对"的程度——严格 schema、强默认、选项极少、机器可校验、错误信息可读；提供 schema 文件与示例。
- **债？** ⚠️ schema 是**契约**：M3 定下后，改动波及所有任务与将来生成它的 AI。故"今天人写、将来 AI 写"要求 schema **现在**就按 AI 友好标准设计，而非事后收紧。
- **设计的双重约束**：YAML 要同时满足"**人写不累**"与"**AI 写不出错**"——前者靠简写与默认，后者靠严格 schema 与可校验性。
- **前置**：依赖 D1 的任务态注入模型稳定。

### D9 上下文工程

- **愿景**：每个 Agent 开跑时带着"恰到好处"的上下文——项目知识、约定、决策、上游产物——而非把一切塞进 prompt。分层：任务内状态注入 → 项目级累积 → 检索/裁剪/注入策略（含各 harness 原生记忆源的选用）。
- **MVP 切片（分段递进）**：
  - **M1 — 结构化记录**：项目级上下文（决策 / 约定 / 已知坑）从 run 产生时即结构化为可累积的存储（只写不注）。
  - **M3 — 项目级注入器**（与调度并行做）：每个 Stage 注入一份**精选后的精简上下文包**，而非原始产物的堆叠；检索/裁剪以最简起步（按 stage 声明的需求选取）。
- **债？** ⚠️ 若 M1 不**结构化记录**，将来"项目记忆"无源可溯——同 D6 / D7 性质。注入器晚做不还债（两者读同一份存储）。
- **为何是必需而非可选**：只做到"任务内状态注入"= 把上游产物全塞进 prompt → **prompt 臃肿**。上下文工程的目的正是把上下文**外置、按需注入**，保持 prompt 精简——这是它要一步做到项目级的原因。
- **独有面**：各 harness 原生记忆源（`CLAUDE.md`、pi 配置 / 会话）由谁管、注入哪个、如何裁剪——现有工具（含 DSH）未覆盖。
- **关系**：D1 的"任务态注入"= 本轴最底层；D9 在其上加"项目级累积"与"精选注入"。

## 5. 演进轴与功能落位

四条**正交**轴（不是台阶）：

```
轴 A — 执行拓扑（活儿怎么跑）
  A1 单机单任务 ─▶ A2 单机常驻 ─▶ A3 多机分布式

轴 B — 认知经济性（你知道什么、优化什么）
  B1 原始日志 ─▶ B2 用量/成本 ─▶ B3 质量/浪费归因 ─▶ B4 按 B2/B3 智能路由

轴 C — 编排表达（你怎么描述要做的事）
  C1 手写 YAML ─▶ C2 规范化 schema（AI 可读）─▶ C3 意图 → AI 生成 DAG

轴 D — 上下文工程（每个 agent 开跑时带着什么）
  无记忆 ─▶ 任务内状态注入 ─▶ 项目级累积 ─▶ 检索/裁剪/注入策略
```

- 四条轴可独立推进：**个人完全可以停在 A2 + B3 + C2 + 项目级上下文**，这是本项目的主甜点区。
- 轴 A/B 的真交汇点在 **B4**（智能路由）；轴 C、D 与它们正交，各自推进。

| 能力域 | 轴 A | 轴 B | 轴 C | 轴 D |
|---|---|---|---|---|
| D1 编排 | A1→A2（→A3 远期） | — | C1 | 任务注入 |
| D2 隔离 | A1 | — | — | — |
| D3 路由 | A1 | B4（远期的智能路由） | — | — |
| D4 审批 | A1 | — | — | — |
| D5 观测 | A2（HTTP 服务） | B1 | — | — |
| D6 用量成本 | A2 | B2 | — | — |
| D7 质量归因 | A2 | B3 | — | — |
| D8 编排生成 | — | — | C1→C2→C3 | — |
| D9 上下文工程 | A2 | — | — | 任务注入→项目级 |

## 6. 优先级（MoSCoW）：从愿景切出 MVP

MVP 定义 = 下列 Must 全部达成（对齐 development-plan 的 M1–M5）。

| 能力 | Must（MVP） | Should | Could / Won't（MVP 外） |
|---|---|---|---|
| D1 编排 | DAG 执行、超时、基础重试 | 条件分支 | 子任务、动态 DAG |
| D2 隔离 | 只读 + worktree + 重叠检测 | — | 内存/文件系统快照、沙箱分级 |
| D3 路由 | 能力匹配 + preferred-first + 降级 | fastest / cheapest | 智能路由（B4） |
| D4 审批 | first-write + merge Gate | path-conflict | push / destructive、策略引擎 |
| D5 观测 | 事件库 + status/logs/diff + HTTP API | 实时跟随 -f、TUI | WebUI、过滤、回放、指标面板 |
| D6 用量成本 | **采集 + `UsageProvider` 位** | 展示、估算成本 | 网关对接、聚合、预算、对账 |
| D7 质量归因 | **记录 config/prompt 版本** | — | 浪费分类、prompt 实验闭环 |
| D8 编排生成 | **YAML schema + 校验，达"AI 可生成"标准** | 示例与模板 | 意图 → AI 生成 DAG（C3） |
| D9 上下文工程 | **M1 项目级上下文结构化记录** | M3 精简注入器、基础检索 / 裁剪 | 各 harness 原生记忆源编排、复杂策略 |
| 多 harness | claude-code / codex / pi 实现（ADR-009） | — | kimi / dsh / gemini 模板 |
| 跨仓库 | 不支持，留扩展（ADR-010） | — | 多 Project 编排 |

**"不产生债"的校验**：Must 里四项加粗的能力（D6 采集、D7 版本记录、D8 schema 契约、D9 上下文结构化）属"现在不做就补不回"或"晚改波及面大"，故强制进 MVP；其余 Should/Could 均为增量可加。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 平台 | Windows 优先可用（统一 UTF-8、路径规范化、进程 kill 可靠） |
| 并发 | 单机多 Run 并发；写入型受 `owned_paths` 与 worktree 约束 |
| 崩溃 | 进程被杀后可查（状态、事件、结果已落库，ADR-005） |
| 资源 | worktree 磁盘占用有上限与清理策略 |
| 安全 | 凭据经 env/本机配置注入，不入 YAML、不入库；事件 `raw` 脱敏；HTTP 本地回环 + token |
| 存储 | SQLite 全量事件（ADR-008），预留 `raw` 分离位 |
| 可维护 | adapter 接口/事件协议版本化；契约测试为输出格式变更的主防线 |

## 8. 边界与约束

- 中转 `api.iottepa.cn` 不支持 `openai-responses`，OpenAI 兼容线路一律 `openai-completions`。
- 各家 CLI 无稳定机器接口：adapter 版本化 + `raw` 保留 + 契约测试。
- 交互式 CLI 优先非交互模式自动化。
- MVP 单仓库、单机（ADR-010）。

## 9. 待探索问题

> 尚未决策、不阻塞 MVP，登记备查。

### 9.1 编排可视化：CLI vs WebUI

**已决（MVP）**：CLI 用**纯文本 `status`**（静态快照，可 grep/重定向、非交互友好）+ `logs -f` 跟随 + `diff` 逐节点。覆盖日常绝大部分信息需求。

**后置（Should）**：
- 全屏 TUI（实时刷新 DAG 图、事件流）——复用同一 Store/API 数据源，纯增量
- WebUI（实时 DAG 图、事件瀑布、逐节点耗时/成本、合并界面、成本面板）——ADR-007 的 HTTP API 使其为纯增量

**真正的约束**：不是渲染层，而是 **HTTP API 是否暴露足够**（DAG 结构、逐 stage/run 状态、事件、指标）。这些本就在数据模型内，故可视化的天花板 ≈ API 的覆盖面。

**两类都做不好的**：agent"推理过程"的可视化。只有事件流，能画的是**结构、状态、指标**，不是它的思考。

### 9.2 TUI 与 WebUI 的关系

- **不冲突**：两者都是渲染层，读同一份 `Store` / HTTP API，**不拥有状态**；交互（merge / approve / cancel）只有一条写路径。
- **前提（唯一耦合点）**：共用同一**实时视图边界**（API + 事件流）。若各自搭一套，同一件事做两遍、行为可能漂移。
- **TUI 是一等公民，非降级品**：WebUI 不会时时可用 / 被用，**无 Web 界面时 TUI 是必备**——故 TUI 优先级不低于 WebUI。
- **待定**：TUI 走 **API**（单一视图边界，天然与 WebUI 同源；顺带充当 API 的第一个消费者/测试）vs **进程内直读 Store**（更简单，但多一条读取路径）。**倾向走 API**。
- **例外**：MVP 的一次性 `status` 快照（非实时）直读 Store、不起服务；真做实时视图时再统一走 API。

## 附录 A：若上升为团队 / 平台工具会如何设计

> 纯探索。个人工具**不应**为这些买单，但了解"哪些是加法、哪些是伤筋动骨"，可指导现在留缝。

### A.1 新增维度

| 维度 | 团队/平台形态 | 对现有设计的影响 |
|---|---|---|
| 身份 | 多用户、登录、RBAC | **需在数据模型有 `actor`/`tenant`**——晚加最贵 |
| 成本归属 | 预算、配额、按人/团队计费 | 依赖 D6，且 usage 需带归属维度 |
| 治理 | 模型白名单、策略引擎、强制审批流 | D4 从"确认点"升级为"策略引擎" |
| 规模 | 分布式 worker、任务队列 | A3；需外部队列/工作流引擎（Temporal） |
| 共享仓库 | 更强的 worktree/合并协调、锁 | D2 需跨机器一致性 |
| 自助接入 | adapter registry / 市场 | ADR-002 插件协议的自然延伸 |
| 可观测 | 仪表盘、SLO、告警 | D5 + 指标层 |

### A.2 关键判断：加法 vs 重写

- **主要是加法**（若缝留好）：规模（换 Store/引擎）、治理（加 Gate/策略）、可观测（加面板）、自助接入（加 adapter）。
- **属于"晚加最贵"**：`tenant`/`actor` 等归属维度、身份与权限、预算归属。这些**渗进数据模型**，越晚越难。
- **结论**：个人工具的 MVP **不必**加 `tenant`，但应避免任何**假定"只有一个用户且永不区分归属"**的接口签名。D6 的 usage 记录，天然就是将来加归属维度的锚点。
