# 后冻契约（形状已知）

> 现在就能画出接口，但 **不写进 M3 也能过**。约束只有一条：Scheduler / Store / Manifest **不得假设这些不存在**（不要焊死单 harness、单消费者、用量只能来自 adapter）。

---

## `RouteStrategy` — M4

```typescript
interface RouteCandidate {
  manifest: HarnessManifest;
  config: HarnessConfig;     // 光有 manifest 不够 createRun
}

interface RouteInput {
  requires: Capability[];
  preferred: string[];
  write: boolean;            // 写入型需 supportsWorktree
  candidates: RouteCandidate[];
  health: ReadonlyMap<string, HealthReport>;
}

interface RouteStrategy {
  order(input: RouteInput): RouteCandidate[];
}
```

默认 `preferred-first`；`cheapest` / `fastest` 为 Should。目标函数效果 > 成本 > 速度（requirements §3）是策略实现的权重，不是接口字段。

## `GateHandler` — M4

approvals 表已在。处理器 = 对某 gate 问 yes/no。

```typescript
interface GateHandler {
  gate: ApprovalGate;
  request(ctx: { taskId: string; runId: string | null; detail: string }): Promise<ApprovalRecord>;
}
```

MVP：`first-write` + `merge` 人工确认。`path-conflict` 为 Should。

## `UsageProvider` — D6 展示层

采集已走 `adapter.collectUsage` → `Store.appendUsage`。Provider 是「还可以从哪读」：

```typescript
interface UsageProvider {
  source: UsageSource;
  fetch(runId: string): Promise<UsageRecord[]>;
}
```

网关实现依赖流量打标（每 run 的 key / 模型别名 / header），否则对不上 runId。M3 只要继续往 Store 写，展示可晚做。

## 平台事件总线 + HTTP — M5 / ADR-007

| 层 | 契约要点 |
|---|---|
| Run 事件流 | **已冻**：`streamEvents` / `Store.listEvents` |
| 总线 | 多 Run → 多订阅者；形状 ≈ `AsyncIterable<{ taskId, event: UnifiedEvent }>` |
| HTTP | 覆盖 run / status / logs / diff / merge；TUI **倾向走 API**（requirements §9.2），故订阅协议与 HTTP 应同源 |

一次性 `hcp status` 快照可直读 Store；实时视图统一走总线/API。

## Merge — M5

输入：`runId` + 人工确认（merge Gate）。输出：应用到目标分支的结果 + 来源 run 记录。依赖 Workspace 已能指出 worktree 路径。不进 Scheduler 热路径。

## YAML JSON Schema 产物 — D8 Should

运行时源是 zod。导出 JSON Schema 给「意图→AI 生成 DAG」是**衍生契约**，语义以 zod / `TaskDefinition` 为准。晚导出不改默认值。

## 刻意不冻成「adapter 直连协议」

adapter 之间没有对等通道。协调 = ContextPack + Store 黑板（02）。若将来要直连，必须新开 ADR 推翻黑板模型，不能从本文件长出来。
